# Language and the explainer

Code: `backend/app/i18n/`. Bundles: `backend/app/i18n/strings/<code>.json`.

## Where wording lives

All of it is on the backend. The frontend holds no locale files. It fetches
`/api/meta/strings?lang=` once per language change and exposes `t(key, args)`
through `lib/store.tsx`.

That placement is what keeps the explanations honest. Eligibility reasons are
generated from rule outcomes, so a sentence cannot drift out of sync with the
rule it describes. If the frontend composed its own wording it would eventually
claim *you qualify because you are over sixty* about a rule testing something
else entirely.

## Phrases, not essays

Sentences are assembled from short reusable phrases keyed by rule. A rule
carries the key and its arguments:

```json
{ "field": "age", "op": ">=", "value": 60, "key": "rule.age_min", "args": { "n": 60 } }
```

```json
"rule.age_min": "You are {n} years or older"
"rule.age_min": "आपकी उम्र {n} साल या उससे ज़्यादा है"
"rule.age_min": "உங்கள் வயது {n} அல்லது அதற்கு மேல்"
```

Twenty such phrases, seventeen under `rule.` and three under `excl.`, cover all
sixteen schemes. A complete bundle is about 210 short strings in total, which is
the whole cost of a new language: no scheme essays get rewritten. Arguments
named `amount` are money-formatted before interpolation, so a threshold renders
as `Rs 2.5 lakh` rather than `250000`.

## Key namespaces

| Prefix | Covers |
|---|---|
| `app.*` | Name, tagline, disclaimer |
| `nav.*`, `action.*` | Chrome and buttons |
| `home.*`, `upload.*`, `profile.*`, `schemes.*`, `vault.*`, `applications.*` | Screen copy |
| `status.*` | Scheme verdicts, long and short forms |
| `explain.*` | Section headings on the explanation page |
| `step.*` | Next-action sentences |
| `rule.*`, `excl.*` | Eligibility reasons |
| `field.*`, `value.*` | Profile field labels and their option labels |
| `doc.*` | Document type names |
| `app_status.*`, `reminder.*` | Tracker statuses and reminder text |

## Fallback, and saying so

`t()` resolves in order: the requested language, then English, then the key
itself. Bundles are cached with `lru_cache`, so **adding keys requires a
backend restart**.

Coverage is measured at runtime rather than assumed:

```json
{ "code": "ta", "native": "தமிழ்", "tts": "ta-IN", "coverage": 0.83, "complete": false }
```

A partial language is served English-backfilled and reported as incomplete, so
the UI can mark it rather than quietly showing English under a Tamil heading. A
malformed or empty bundle file is caught and treated as absent, so a
half-finished translation cannot take the app down.

Scheme prose lives inside `schemes.json` as `{ "en": ..., "hi": ... }` blocks
rather than in the string bundles, because it is per-scheme rather than
reusable. Tamil scheme descriptions are deliberately absent: a subtle
mistranslation of a benefit is worse than showing English, when the reader is
deciding whether they are owed money.

## Text to speech

Every language row carries a BCP-47 `tts` tag. The explanation endpoint returns
`speech_text`, a flat string that stitches the sections into sentences, because
bullet fragments run together when read aloud.

`SpeakButton` checks `speechSynthesis.getVoices()` for a voice matching the
language and **hides itself if none exists**, rather than reading Hindi in an
English accent. Rate is set slightly below normal.

This is the single most useful affordance in the app for somebody who cannot
read comfortably, and it costs nothing, because the speech engine is already on
the device.

## Adding a language

1. Copy `backend/app/i18n/strings/en.json` to `<code>.json` and translate the
   values. Leave the keys alone. Keep `{placeholders}` intact.
2. Add a row to `LANGUAGES` in `backend/app/config.py`:

```python
"bn": {"label": "Bengali", "native": "বাংলা", "tts": "bn-IN"},
```

3. Optionally add `"bn"` blocks to `name`, `full_name`, `department`, `benefit`
   and `apply_offline` in `backend/data/schemes.json`.
4. Restart the backend.

No frontend change. The language switcher renders from
`/api/meta/languages`, and a partial translation is reported as partial rather
than passed off as finished.

Translate the highest-visibility keys first: `nav.*`, `action.*`, `status.*`,
`rule.*`, `explain.*`, `field.*`, `doc.*`. Those dominate the screen. Long prose
under `home.*` and `upload.*` can fall back to English for longer without the
app feeling broken.

## Writing guidance

The audience includes people with limited literacy reading on a cracked phone
screen. Wording should:

- use short sentences and everyday words, aiming around a grade five reading
  level
- address the person directly, as in *You have a bank account*
- state facts rather than jargon: *below the poverty line* rather than *BPL
  category as per SECC*
- never promise an outcome. The app explains and prepares; only the government
  office decides, and `app.disclaimer` says so on every screen
